# 易經卦象規則規格書

- **版本**：v0.1
- **日期**：2026-09-03
- **狀態**：第一版工程規則；承／乘為一般規則，不代表涵蓋所有卦例特殊取象
- **適用專案**：`projects/iching-research/`

## 1. 規格目的

定義第一版網站可以由程式穩定執行、由測試驗證、並能回鏈研究來源的卦象計算規則。本規格只處理揲蓍法、爻值、卦象轉換與基本結構標籤，不處理個人化吉凶占斷。

## 3. 六爻資料方向

程式內部固定採由下往上：

```text
lines[0] = 初爻
lines[1] = 二爻
lines[2] = 三爻
lines[3] = 四爻
lines[4] = 五爻
lines[5] = 上爻
```

畫面上的卦象圖則將 `上爻` 顯示在上方，並以文字說明閱讀方向。

## 4. 揲蓍法

### 4.1 基本數量

1. 取 50 根蓍草。
2. 固定置一不用，實際演算 49 根。
3. 一變由四營組成：分二、掛一、揲四、歸奇。
4. 三變得到一爻。
5. 六爻共十八變完成一卦。

### 4.2 一變輸出

令本次起始本數為 `initialStalks`：

1. 分二：將蓍草分成左、右兩組，兩組各至少一根。
2. 掛一：從右組取一根，視為掛一。
3. 揲四：左右兩組分別以四計數；餘數為 0 時記作 4。
4. 歸奇：
   - 第一變：`overCount = 1 + leftRemainder + rightRemainder`，結果為 5 或 9。
   - 第二、三變：結果為 4 或 8。
5. 下一次使用 `initialStalks - overCount` 根。

每一變至少保存：

```text
initialStalks
leftStalks
rightStalks
rightAfterHangingOne
leftRemainder
rightRemainder
overCount
remainingStalks
```

### 4.3 數位模擬限制

「隨意分握」沒有唯一數位隨機分布模型。第一版標示為「揲蓍法數位模擬」，不宣稱完全重現人手操作。亂數來源必須可注入，以便測試使用固定結果。

## 5. 三變與爻值

將每一變的過揲結果分類：

- 4、5：少數
- 8、9：多數

三變中多數的數量對應：

| 多數數量 | 爻值 | 狀態 | 本卦陰陽 | 變爻 | 變後 |
|---:|---:|---|---|---|---|
| 0 | 6 | 老陰 | 陰 | 是 | 陽 |
| 1 | 8 | 少陰 | 陰 | 否 | 陰 |
| 2 | 7 | 少陽 | 陽 | 否 | 陽 |
| 3 | 9 | 老陽 | 陽 | 是 | 陰 |

只有 6、9 是變爻。

## 6. 本卦與之卦

1. 6、8 視為陰爻；7、9 視為陽爻，組成本卦。
2. 6 轉為陽；9 轉為陰；7、8 不變，組成之卦。
3. 變爻位置以 1～6 保存，不能只保存顯示名稱。
4. 乾卦六爻皆變時保留 `用九` 資料入口；坤卦六爻皆變時保留 `用六` 資料入口。

## 7. 六十四卦 mapping

八卦採由下往上的三爻 pattern：

| 卦 | pattern |
|---|---|
| 乾 | 111 |
| 坤 | 000 |
| 震 | 100 |
| 巽 | 110 |
| 坎 | 010 |
| 離 | 101 |
| 兌 | 011 |
| 艮 | 001 |

六爻 pattern 由下卦三爻接上卦三爻。六十四卦 mapping 必須：

- 卦序完整為 1～64。
- 每一組上下卦只對應一卦。
- 賁卦採標準「山火賁」：上艮、下離；參考 DOCX／PDF 目錄中的「火山賁／艮下離上」須標記為待校訂差異。

## 8. 位置與中位

### 8.1 得位／失位

- 陽位：初、三、五。
- 陰位：二、四、上。
- 陽爻居陽位，或陰爻居陰位：得位／位正。
- 陽爻居陰位，或陰爻居陽位：失位／位不正。

### 8.2 得中／不中

- 二爻、五爻為中位。
- 得中只描述位置，不代表一定得位。
- 得位與得中必須分成兩個欄位與兩個 UI 標籤。

## 9. 應

固定對應位置：

```text
初 ↔ 四
二 ↔ 五
三 ↔ 上
```

- 對應兩爻一陰一陽：`正應`。
- 對應兩爻同陰或同陽：`無正應`。
- 第一版顯示對應爻位與判定結果，不由此產生吉凶結論。

## 10. 承／乘：一般規則 v1

### 10.1 適用範圍

本節只是一套可測試的相鄰陰陽結構規則，來源中的特殊卦例取象不自動覆蓋。本規則版本識別為：

```text
general-adjacent-yin-yang-v1
```

### 10.2 判斷

只以陰爻作為關係主體：

- 陰爻下方緊鄰陽爻：陰爻標記 `乘剛`，並記錄下方陽爻位置。
- 陰爻上方緊鄰陽爻：陰爻標記 `承陽`，並記錄上方陽爻位置。
- 陰爻上下都鄰接陽爻時，可同時有 `乘剛` 與 `承陽`。
- 陽爻不反向標記「承」或「乘」。
- 相鄰同性不產生承／乘標籤，但仍可保存相鄰資料。

資料輸出：

```text
{
  kind: "承陽" | "乘剛",
  linePosition: number,
  adjacentPosition: number,
  ruleVersion: "general-adjacent-yin-yang-v1"
}
```

### 10.3 特殊例外

來源可能在特定卦例中使用反向或情境化語句，例如「三陽承四陰」。這類內容屬於個別卦例取象，不在一般規則 v1 中自動套用；若日後支援，必須建立獨立的卦例規則或 `ruleProfile`。

## 11. 不在本規格的項目

- 多爻變時朱熹體例、南懷瑾體例與古筮案例的主次占斷。
- 比的完整全局判斷矩陣。
- 納甲、五行六親、月建日辰、世應、神煞。
- 互卦、錯卦、綜卦的自動占斷。
- 個人化吉凶、醫療、投資、法律或行動建議。

## 12. 測試要求

至少需要測試：

1. 每變的過揲數值只產生合法結果。
2. 三變能正確得到 6、7、8、9。
3. 六爻順序由初至上。
4. 6、9 變爻翻轉；7、8 不翻轉。
5. 六十四卦 mapping 無缺號、重複或錯位。
6. 得位與得中分開判斷。
7. 應位三組正確。
8. 陰爻上下鄰陽時的承／乘方向正確。
9. 同一陰爻同時上下鄰陽時可得到兩種關係。
10. 特殊卦例不會無來源地改寫一般規則。

## 13. 384 爻資料管線

### 13.1 標準資料檔

網站使用的 384 筆爻資料位於：

```text
projects/iching-research/src/data/iching/line-records.json
```

資料集版本為 `iching-line-records-v1`，包含：

- `records`：64 卦 × 6 爻 = 384 筆。
- `specialLines`：乾卦 `用九`、坤卦 `用六`。
- `source`：主要來源、抽取稿類型與整體校訂狀態。
- 每筆 record：`id`、`hexagramSequence`、`hexagramName`、`position`、`name`、`text`、`xiaoxiang`、`reviewStatus`、`sourceRef`。

目前所有內容為來源初稿，`reviewStatus` 固定為 `待校訂`；未完成人工校訂前不得視為正式定稿。泰上六與離上九的小象已依人工校訂補入；後續若來源仍有欄位缺漏，驗證器會以 warning 提示，網站不自行補寫。

### 13.2 匯入與驗證

抽取工具不直接讀取或改寫原始 DOCX／PDF，而是接收外部產生的 UTF-8 文字抽取稿：

```bash
cd projects/iching-research
npm run content:import -- \\
  --input /path/to/hexagrams-docx.txt \\
  --input-label "DOCX 文字抽取稿" \\
  --source "參考資料/易經六十四卦_白話 Final_Mike 2026.docx" \\
  --output src/data/iching/line-records.json
```

匯入後必須執行：

```bash
npm run content:validate
```

兩份抽取稿可用下列指令產生雙來源差異報告：

```bash
npm run content:compare -- \\
  --docx /path/to/hexagrams-docx.txt \\
  --pdf /path/to/hexagrams-pdf.txt \\
  --output ../../research/易經網站/content-diff/report.json \\
  --markdown ../../research/易經網站/content-diff/report.md
```

報告以 `卦序-爻位` 比對爻名與爻辭，並忽略 PDF 頁碼、空白與一般標點差異；差異清單只供人工校訂，不會自動覆蓋標準資料。驗證失敗時不得將 JSON 接入網站。驗證器會檢查 64 個卦序、每卦 1～6 爻、總數 384、唯一 id、非空爻辭、來源定位，以及只存在乾／坤的兩筆特殊爻。

### 13.3 內容校訂流程

1. 以 DOCX 與 PDF 交叉比對原文、爻名與斷句。
2. 針對異體字、OCR 錯字、括號註記與來源差異建立人工校訂紀錄。
3. 校訂完成後才可將個別 record 的 `reviewStatus` 改為新的狀態值；同時保留原始初稿與來源定位。
4. 校訂資料變更後重新執行 `npm run content:validate`，再執行網站測試與建置。

網站的「資料校訂」頁提供 384 筆逐爻搜尋、狀態篩選、文字／備註編輯與 JSON 匯出。瀏覽器編輯內容只保存在 `localStorage` 的 `iching-research:line-review-draft`，不會直接改寫 `line-records.json`；正式合併前仍須人工審核匯出檔。
