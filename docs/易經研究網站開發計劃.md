# 易經研究網站開發計劃

- **版本**：v1.0
- **日期**：2026-09-03
- **狀態**：待確認
- **依據**：`docs/易經研究網站產品需求文件.md`
- **第二版研究室計畫**：`docs/易理研究室第二版規格、需求與開發計畫.md`
- **建議技術**：React、TypeScript、Vite；最終以建立專案時確認的穩定版本為準

## 1. 開發原則

1. 先驗證規則與資料，再製作最終視覺。
2. 揲蓍計算、卦象 mapping、結構分析與 UI 分離。
3. 先以少量代表卦完成端到端流程，再擴充至 64 卦與 384 爻。
4. 不在 MVP 混入納甲、五行六親或一卦六伏等進階引擎。
5. 每階段完成一個可獨立驗證的成果，不等待全部做完才測試。

## 2. 建議專案位置

```text
projects/iching-research/
├── src/
│   ├── app/
│   ├── components/
│   ├── domain/iching/
│   ├── features/divination/
│   ├── features/hexagrams/
│   ├── features/glossary/
│   └── data/
├── tests/
├── public/
└── package.json
```

研究來源與決策繼續保存在工作區的 `research/易經網站/`，不複製進程式 bundle。

## 3. 工作分解

### Phase 0：規格封版與測試案例

**目標**：讓工程規則沒有方向性歧義。

工作：

- 建立 `docs/易經卦象規則規格書.md`。
- 定義揲蓍法每一變的輸入、輸出與有效狀態。
- 決定數位分草隨機策略。
- 定稿得位、得中、應、承／乘規則及來源。
- 建立至少 8 組人工案例：
  - 爻值 6、7、8、9 各至少一組。
  - 0、1、2、3、4、5、6 個變爻均有案例。
  - 乾卦六變與坤卦六變特殊案例。
- 確認 DOCX 或 PDF 的主要內容底稿。

產出：

- 規則規格書。
- 人工案例與預期結果表。
- 第一版資料 schema。

驗證／Gate：

- 每條規則有來源、輸入、輸出與例外說明。
- 承／乘方向經人工確認。
- 隨機策略可測試且不依賴動畫時間。

對應需求：`CALC-*`、`STRUCT-*`、`CAST-10`。

### Phase 1：專案骨架與設計基礎

**目標**：建立可測試、可路由、可逐步擴充的前端專案。

工作：

- 建立 React + TypeScript + Vite 專案。
- 設定 formatter、lint、typecheck、unit test 與 build。
- 建立首頁、起卦、結果、六十四卦、單卦、術語路由。
- 建立全站版型、header、主要 navigation、錯誤頁。
- 建立基本 design tokens：色彩、字體、間距、focus、動態效果。
- 設定 `prefers-reduced-motion` 與 360px responsive baseline。

產出：

- 可啟動的網站骨架。
- 所有主要路由可到達。
- CI 或本機一鍵驗證指令。

驗證／Gate：

```bash
npm run lint
npm run typecheck
npm test
npm run build
```

對應需求：`HOME-*`、資訊架構、非功能需求。

### Phase 2：領域模型與規則引擎

**目標**：不依賴 UI，完成可驗證的易經計算核心。

建議模組：

```text
src/domain/iching/
├── types.ts
├── yarrow.ts
├── lines.ts
├── trigrams.ts
├── hexagrams.ts
├── transform.ts
├── relationships.ts
└── validation.ts
```

工作：

- 定義爻值、陰陽、爻位、三變紀錄與起卦 Session 型別。
- 實作每變的分二、掛一、揲四、歸奇。
- 實作三變轉成 6／7／8／9。
- 實作本卦與之卦轉換。
- 建立八卦與六十四卦 mapping。
- 實作得位、得中、應及已定稿的承／乘規則。
- 為 RNG 建立可注入介面，測試使用 deterministic stub。

單元測試：

- 各爻值案例。
- 每變的數值不變量。
- 初爻至上爻順序。
- 64 卦 mapping 全量測試。
- 0～6 變爻。
- 結構規則與人工案例。

驗證／Gate：

- 所有 Phase 0 人工案例通過。
- 領域模組不匯入 React 或瀏覽器 API。
- 相同 RNG stub 必須得到相同結果。

對應需求：`CALC-*`、`STRUCT-*`。

### Phase 3：揲蓍法逐步互動

**目標**：完成可恢復、可返回、可加速的十八變互動。

建議元件：

```text
DivinationSetup
CastingProgress
YarrowOperation
StalkGroups
ChangeSummary
LineSummary
CastReview
RestartDialog
```

工作：

- 起卦問題輸入與說明頁。
- 詳細模式：每個四營步驟按一次。
- 「自動完成本變」模式。
- 顯示第幾爻、第幾變、總進度與數值。
- 三變完成時顯示爻值與老少陰陽。
- 六爻由下向上逐步建立。
- 實作返回、重新開始確認與 `sessionStorage` 恢復。
- 實作鍵盤操作、focus 管理與減少動畫。

測試：

- 狀態機轉移測試。
- 詳細模式與自動完成本變產生相同結果。
- 重整恢復、返回與重新開始。
- 無法在十八變前進入結果頁。

驗證／Gate：

- 桌面與 360px 手機可完成全流程。
- 鍵盤可操作所有主要按鈕。
- 動畫關閉後功能不受影響。

對應需求：`SET-*`、`CAST-*`。

### Phase 4：結果頁與結構分析

**目標**：完成產品最核心的卦象理解與經文閱讀流程。

建議元件：

```text
HexagramOverview
HexagramFigure
LineComparison
StructureSummary
StructureTag
ChangingLineCard
ChangedJudgment
SourceDisclosure
```

工作：

- 本卦與之卦並列。
- 六爻、爻值、陰陽與變爻視覺化。
- 顯示所有變爻與本卦爻辭。
- 實作 0 個變爻狀態。
- 3～6 個變爻顯示之卦卦辭。
- 顯示得位、得中、應、承／乘標籤與判定理由。
- 原文、象、注、釋與來源摺疊分層。
- 灰階、鍵盤與螢幕閱讀器檢查。

測試：

- 0～6 個變爻的結果頁元件測試。
- 所有變爻都沒有遺漏或取錯卦。
- 之卦卦辭顯示門檻正確。
- 本卦與之卦文字不混淆。

驗證／Gate：

- 使用人工案例逐筆核對結果。
- 變爻不靠顏色也能辨認。
- 每個結構標籤均能找到定義與來源。

對應需求：`RESULT-*`、`STRUCT-*`。

### Phase 5：內容資料管線

**目標**：將本機 DOCX／PDF 內容整理成可驗證的網站資料。

工作：

- 定義 Hexagram、Line、SourceRef schema。
- 建立 DOCX／PDF 抽取後的正規化腳本；原始參考檔保持唯讀。
- 解析卦序、卦名、上下卦、卦辭、彖、象、注、釋。
- 解析 384 爻及乾用九／坤用六。
- 產生 validation report：缺卦、重複卦、缺爻、重複爻、空欄位。
- 建立人工校訂流程與 `reviewStatus`。
- 先完成代表卦：乾、坤、臨、損及一組多變爻案例所需之卦。
- 代表卦驗證通過後，再擴充至全部 64 卦。

測試：

- 卦序必須恰為 1～64。
- 每卦恰有 position 1～6。
- 爻總數恰為 384。
- 乾有用九、坤有用六，其他卦不得誤有特殊爻。
- 上下卦 mapping 與 8×8 索引一致。

驗證／Gate：

- 自動資料驗證全部通過。
- 發布內容達到約定校訂狀態。
- 不將 NotebookLM 回答中的錯誤索引帶入網站資料。

對應需求：資料需求、內容來源原則、`DETAIL-*`。

---

### Phase 6：六十四卦與術語頁

**目標**：完成不需起卦也能使用的研究閱讀功能。

工作：

- 桌面 8×8 六十四卦矩陣。
- 手機版篩選與卡片列表。
- 卦名、卦序搜尋。
- 單一卦詳細頁與六爻摺疊內容。
- 術語索引與詳細說明。
- 從結果頁連回卦與術語頁。
- 顯示來源與校訂狀態。

測試：

- 64 個卦頁路由均可到達。
- 搜尋與上下卦篩選正確。
- 384 爻資料可於正確卦頁讀取。
- 結果頁深連結不遺失閱讀位置。

驗證／Gate：

- 桌面矩陣及手機列表均可完整瀏覽。
- 內容分層與來源標示一致。

對應需求：`HEX-*`、`DETAIL-*`、`TERM-*`。

### Phase 7：整合驗收與發布準備

**目標**：確認完整流程、內容與可用性達到發布標準。

工作：

- 端到端測試：首頁至完成起卦與結果閱讀。
- 人工測試 0～6 個變爻案例。
- Responsive、鍵盤、灰階及減少動畫檢查。
- 錯誤狀態與 Session 恢復測試。
- 效能與 bundle 檢查。
- 內容與來源抽樣校對。
- 建立部署設定與隱私說明；部署前另行取得使用者確認。

發布 Gate：

- lint、typecheck、unit、component、E2E、build 全部通過。
- PRD 的 P0 驗收條件全部完成。
- 64 卦、384 爻及用九／用六資料驗證通過。
- 沒有個人化吉凶、醫療、投資或法律斷言。
- 使用者確認正式名稱、視覺及部署目標。

## 4. 建議里程碑

| 里程碑 | 包含階段 | 可展示成果 |
|---|---|---|
| M1 規則核心 | Phase 0～2 | 用測試資料輸入六爻，得到正確本卦、之卦與結構標籤 |
| M2 起卦原型 | Phase 3 | 可完成逐步揲蓍與恢復 Session |
| M3 結果原型 | Phase 4 | 可完整展示變爻、結構與之卦卦辭 |
| M4 內容版 | Phase 5～6 | 可查閱完整六十四卦與 384 爻 |
| M5 發布候選 | Phase 7 | 通過整合、可用性與內容驗收 |

## 5. 相依關係

```text
規則定稿
├──→ 規則引擎 ─→ 揲蓍互動 ─→ 結果頁
└──→ 資料 schema ─→ 內容管線 ─→ 卦與術語頁
                                   ↓
                              整合驗收
```

關鍵路徑：

1. 分草隨機策略未定稿，不能封版 `yarrow.ts`。
2. 承／乘方向未人工確認，不能在結果頁標為正式判斷。
3. 內容 schema 未定稿，不能大量整理 384 爻。
4. 完整資料與結果頁可平行開發，但發布前必須整合驗證。

## 6. 測試策略

| 層級 | 測試重點 |
|---|---|
| Unit | 揲蓍、爻值、卦象轉換、64 卦 mapping、結構規則 |
| Schema/Data | 64 卦、384 爻、用九／用六、來源與校訂狀態 |
| Component | 進度、卦象、變爻卡、3 爻以上之卦卦辭 |
| Integration | Session 狀態、起卦到結果、內容查找 |
| E2E | 詳細模式、自動完成本變、返回、重整、手機版 |
| Manual | 經文校訂、承／乘案例、視覺、鍵盤與灰階辨識 |

## 7. 風險與控制

| 已知問題 | 影響 | 控制方式 |
|---|---|---|
| PDF／DOCX 有錯字、OCR 與斷句問題 | 經文可能錯置 | 保留原文、雙來源對照、reviewStatus、人工校訂 |
| NotebookLM 回答曾產生錯誤爻位索引 | 規則或資料污染 | 只採有引用結論，對照來源全文與人工案例 |
| 多套斷卦體例互相衝突 | 結果不一致 | MVP 不自動選派；rule profile 物理隔離 |
| 數位分草不等於實物分草 | 使用者誤解 | 明確標示模擬，定稿 RNG 規格並做統計測試 |
| 18 變流程過長 | 使用者中途離開 | 提供自動完成本變、進度與 Session 恢復 |
| 長文資料量大 | 首次載入變慢 | 路由／資料分割，按需載入單卦內容 |

## 8. 開工前決策清單

開始 Phase 1 前建議依序確認：

1. 專案位置是否採 `projects/iching-research/`。
2. 是否接受 React + TypeScript + Vite。
3. 正式產品名稱可先用工作名，之後再定。

開始 Phase 2 前必須完成：

1. 分草隨機策略。
2. 承／乘與應的規則規格。
3. 人工測試案例。

開始 Phase 5 前必須完成：

1. 主要內容底稿選擇。
2. 資料 schema 與校訂狀態規則。
3. 內容使用與引用邊界確認。

## 9. 建議下一步

先執行 Phase 0，建立 `docs/易經卦象規則規格書.md` 與人工測試案例；完成後再建立 React 專案骨架。這能避免互動畫面完成後，因揲蓍或承／乘規則改變而重寫核心流程。
