# PI-code-2026 工作治理機制導入計劃書

- **版本**：v0.1
- **建立日期**：2026-08-29
- **目前狀態**：第一階段已導入，進入觀察期
- **適用範圍**：Vibe Coding、程式學習、程式工具研究、技術資料研究與分析
- **決策原則**：先借用治理方法，再依實際使用量增加自動化；不整套複製 AI 辦公室

## 1. 導入目標

建立一套輕量、可驗證、可交接的 Pi 工作流程，讓每次工作都能：

1. 先釐清目標與驗收條件。
2. 依任務複雜度使用適當的規劃與驗證程度。
3. 將程式碼、測試結果、研究證據與學習紀錄分開管理。
4. 避免未經確認的不可逆操作、過度設計與無證據的風險警告。
5. 在需要時留下可供下一次工作接續的資訊。

## 3. 目標工作區架構

```text
PI-code-2026/
├── AGENTS.md                         # 工作規則與安全邊界
├── .pi/
│   ├── settings.json                 # Pi 專案設定
│   ├── skills/                       # 可重複使用的工作方法
│   ├── prompts/                      # 工作入口與驗收流程
│   └── extensions/                   # 未來才加入的工具能力
├── projects/                         # 實際程式專案
├── research/                         # 技術研究、來源與證據
├── learning/                         # 程式學習地圖與筆記
└── task-runs/                        # 僅 L2／L3 任務的必要追蹤紀錄
```

### Source of Truth 分工

| 資料類型 | 主要位置 | 原則 |
|---|---|---|
| 程式碼與測試 | `projects/<project>/` | 程式專案本身是唯一事實來源 |
| 研究證據 | `research/<topic>/` | 保存來源、日期、關鍵證據與判讀 |
| 學習狀態 | `learning/` | 保存學習地圖、筆記與待複習項目 |
| 任務過程 | `task-runs/` | 只做追蹤，不取代程式碼或研究正文 |
| 工作規則 | `AGENTS.md`、`.pi/skills/` | 穩定規則與可重複方法分開管理 |

## 4. 分階段導入路線

### Phase 1：核心治理與問題釐清

- **期間**：2026-08-29～2026-09-12
- **狀態**：已導入，觀察中
- **本階段內容**：
  - `task-governance`
  - `problem-decomposer`
  - 現有 `vibe-coding`
  - 現有 `/work-start`、`/work-review`、`/work-finish`
  - 導入計劃到期提醒
- **使用目標**：先讓日常工作形成「目標 → 小步驟 → 驗證 → 回報」的穩定習慣。
- **通過條件**：至少完成 3 次實際程式或研究任務，並觀察流程是否太重、是否真的減少遺漏。

本階段不導入資料庫、Session 自動摘要、Subagent 或新的 npm package。

### Phase 2：研究與學習支援

- **預定檢視日**：2026-09-12
- **啟動前提**：Phase 1 至少完成 3 次實際任務，且使用者確認要進行。
- **候選內容**：
  - `learning-map-builder`
  - 將 `teacher-fit-evaluator` 改成通用的 `resource-evaluator`
  - 建立 `research-workflow`
  - 視需求改寫 `file-to-markdown`
- **預期用途**：評估 GitHub Repo、Framework、課程、文章、工具與技術方案，並建立可回鏈的研究紀錄。
- **限制**：不直接搬入原版；先移除硬編碼路徑、Claude／Cowork 專屬說明與不存在的外部 Skill 依賴。

### Phase 3：選擇性記憶與自動化

- **預定檢視日**：2026-09-26
- **啟動前提**：Phase 2 已使用至少兩週，或累積 10 次以上 L2／L3 任務，且確實需要跨 Session 接續。
- **候選內容**：
  - 簡化版 Session Continuity
  - 手動儲存與召回工作摘要
  - Skill 使用紀錄與候選改進
  - 必要時才評估 Learning Store
- **預設設定**：不自動注入記憶、不保存 thinking、不保存完整 ToolResult、不保存密鑰或個人敏感資料。
- **決策閘門**：先提出設計與資料邊界，經使用者確認後才實作。

### Phase 4：Skill 管理成熟化（非固定日期）

只有在 Skills 數量明顯增加，或出現重複、觸發衝突、品質回歸時才考慮：

- `skill-master`
- `skill-curator`
- Skill eval、baseline 與版本治理

這一階段不以日期自動啟動，以實際維護成本作為條件。

### 本階段的使用規則

- L0：一般問答或單一檔案讀取，不建立任務紀錄。
- L1：單一步驟修改，只確認產出存在與位置。
- L2：多步驟工作，先列 1～3 個成功條件，必要時建立 `task-runs/` 紀錄。
- L3：修改規則、Skill、設定或高影響內容，必須說明範圍並做完整驗證。
- 沒有證據的風險只標示為未知，不直接當成錯誤。
- 一次性經驗不自動升格為永久規則或記憶。

## 6. 到期提醒規則

每次執行 `/work-start` 或開始非 L0 工作時，先檢查本計劃的預定檢視日與完成條件：

1. 到達 2026-09-12，提醒檢視 Phase 2。
2. 到達 2026-09-26，提醒檢視 Phase 3。
3. 若尚未達到 Phase 1 的實際任務數，提醒應以「觀察尚未完成」為主，不提前導入。
4. 提醒只代表進行 Review，不代表自動修改、安裝或啟用下一階段。
5. 進入下一階段前，必須先向使用者報告建議與影響，取得確認後才執行。

Pi 沒有在工作區關閉時主動推播訊息的背景排程能力，因此提醒會在下次使用此工作區、執行 `/work-start` 或重新討論本計劃時出現；不會假裝已建立系統通知。

## 7. 驗證方式

每一階段完成後，至少檢查：

- 新增檔案存在且位於正確位置。
- Skill frontmatter 可被 Pi 識別。
- 觸發描述沒有與既有 Skill 明顯衝突。
- Prompt、Skill 與 `AGENTS.md` 的路徑一致。
- 沒有引入不必要的套件或私人資料。
- 實際執行一個代表性任務，確認流程沒有過度增加負擔。
- `git diff` 只包含本階段必要變更。
